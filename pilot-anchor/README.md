# pilot-anchor (Stage 1 ① / Stage 2 ②③)

リーチデシジョン (指を離さず2択へドラッグ) 課題。修論研究「モバイル入力ダイナミクスから調査回答の確信度を推定する」のパイロット。**ブロック駆動**で、同じアプリを `?block=` で切り替える:

- **① 数値サイズ一致性** (既定、Stage 1 = 装置妥当性確認。Ouellette Zuk 2025。評定なし): 取得系が先行研究の「難易度→運動指標」効果を再現するか。
- **② 価値・選好** (`?block=value`、Stage 2。評定ON): trial 直後の主観評定 (自信・迷い) を軌道から予測できるかの本筋。文字2択で価値差を段階化。
- **③ 道徳ジレンマ** (`?block=moral`、Stage 2。評定ON): 場面文＋文字2択。4類型 × 葛藤3水準で葛藤の強さを段階化。
- **②③ 統合** (`?block=combo`、第二パイロット配布用): ②と③を1セッションで実施。ブロック順は既定ランダム (被験者間CB、`?order=vm|mv` で固定可)。**⑤注意チェック込み** (既定ON、`?attn=0` で無効化)。

**公開URL**: ① <https://and-space83.github.io/drag-survey/pilot-anchor/> / ② <https://and-space83.github.io/drag-survey/pilot-anchor/?block=value> / ②③統合 <https://and-space83.github.io/drag-survey/pilot-anchor/?block=combo>
リポ全体のアプリ一覧は [../README.md](../README.md) を参照。

## このアプリの目的

研究全体の主問いは「ドラッグ軌道から各設問への主観的確信度を機械学習で予測できるか」。本アプリはその前段で、**「Web × モバイル × ドラッグ」という取得系が、先行研究で確立した『難易度 → 運動指標』の効果を再現するかを実機で確認**するためのもの。アンカー課題は客観難易度が既知なので、本実験の本筋 (主観確信度予測) に進む前の妥当性確認として使う。

主観評定は **① アンカーでは取得しない**方針（タスクの性質上、確信度は構成的に変動しないため）。評定は **②③ (`?block=value` / `?block=moral` / `?block=combo`) で有効化**され、各試行直後に**2項目 (自信・迷い) ×5段階**を提示する (`CONFIG.ratings`。難しさは第三パイロットで削除)。

## 参加者の動作

1. スマートフォンで URL を開く（アプリインストール不要）
2. 必須: ニックネーム(ローマ字)・年齢・機種名・性別(回答しない可)・利き手を入力 (事前アンケート、全項目そろうと開始可)
3. **環境音チェック** (マイク必須): マイクを許可して周囲の音量を確認。静かな環境になるまで先へ進めない。**測定は音量レベルのみで音声の内容は記録・送信されない**。moral を含むセッションでは続けて**読速ベースライン** (短文3本を読了タップ)
4. 練習 (チュートリアル+行動ゲート: ①は正解3連続・②③は有効ドラッグ2連続で本番へ。未達なら練習を自動補充。評定ブロックでは練習1問目に評定チュートリアル5ページ) → 本番 (①84 / ②24 / ③24 / ②③統合48+注意チェック 試行、約 5–10 分)。統合 (`combo`) は冒頭に統合練習 (各ブロック2問)
5. 各試行: 下中央の START に指を置く → 選ぶ方のボックス (①は数が大きい方) へ**指を離さず**ドラッグ → 離す (評定ブロックは直後に自信・迷いの2項目評定)。課題中に周囲が騒がしくなると、評定送信後に「静かな場所で続けてください」の画面が入る
6. 完了直後に「直前どう持って・どの指で操作したか」を1つ選択 (事後アンケート、5択)。評定ブロック (②③) ではさらに使いにくさアンケート (複数選択+自由記述) が末尾に1回出る
7. **データは自動送信**される (「✅ 送信完了」表示)。完了画面に**完了コード** (XXXX-XXXX) が表示される (募集サイト経由の場合は納品欄に入力してもらう。`?ccode=0` で非表示)
   - 自動送信に失敗した場合のみ「データを保存 (JSON)」「データを送る (共有)」ボタンが現れ、手動で研究者に送れる (LINE / メール / Drive)
   - 中断後に再訪すると、前回データの保存ボタンが intro 画面に出る

> 事前=特性 (年齢・性別・利き手)、事後=状態 (持ち方+操作した指=grip) と分けるのは、操作手を事前に意識させて自然な使い方が崩れるのを避けるため。

## 記録されるデータ (1試行あたり)

- **Pointer Events 列**: `pointerdown` / `pointermove` / `pointerup`、raw `event.timeStamp`、surface 相対座標、Android Chrome の `getCoalescedEvents` 含む
- **試行メタ**: 数値ペア・congruency・大きい数の左右位置・選択結果・正誤・RT/MT/total の proxy
- **参加者属性**: ニックネーム・年齢・機種名・性別・利き手 (事前) / grip=持ち方+操作した指 (事後、5択)
- **端末情報**: UA・画面サイズ・DPR・推定リフレッシュレート
- **geometry スナップショット**: 試行ごとの START / 選択肢 / surface 位置 (空間正規化用)
- **実効サンプリングレート**: `dt>0` ガード付き
- **実施環境・品質 (2026-07-21/22 追加)**: 環境音レベル要約 `noise:{n,meanDb,maxDb,overMs}` (音量のみ・生音声なし)・ノイズゲート滞在 `noisePause`・画面離脱 `vis:{count,totalMs}`・`device.{mic, wakeLock, completionCode, readingBaseline}`

完全な data spec は [`index.html`](index.html) 冒頭のコメントを参照。

## 設定 (URL クエリで上書き可)

| パラメータ | 既定 | 内容 |
|---|---|---|
| `?block=` | anchor | 実行ブロック (`anchor`=①数値サイズ / `value`=②価値・選好 / `moral`=③道徳ジレンマ / `combo`=②③統合)。既定値は各ブロックで変わる |
| `?order=` | ランダム | `combo` のブロック順 (`vm`=②→③ / `mv`=③→②)。未指定は端末ごとランダム=被験者間CB |
| `?attn=0` | ON (combo) | ⑤注意チェックの無効化 (combo では既定ON) |
| `?reps=N` | ①7 / ②③1 | 反復数 (①12セル×7=84 / ②24項目×各1回=24 / ③24項目×各1回=24。reps を増やすと②③は項目を複数回・両側に出す) |
| `?practice=N` | ①6 / ②③2 | 練習バッチ数 (行動ゲート未達なら自動補充されるため実際の練習数は増えうる)。`?practice=0` は練習スキップ=**開発専用** (配布URLに付けない) |

## 課題仕様

- **刺激**: アラビア数字、物理サイズ比 2:1 (大: `--choice-w` の 22vmin、小: 11vmin)
- **数値ペア**: `1v2` / `2v8` / `8v9` (距離が小さい `8v9` がサイズ効果で最難)
- **congruency**: congruent (大きい数が物理的にも大) / incongruent (大きい数が物理的に小)
- **左右カウンターバランス**: 大きい数の左右配置を均等にして右手バイアスを統制
- **試行構成**: 2 × 3 × 2 = 12 セル × 7 反復 = **84 本番試行**

レイアウト (片手操作向け) は CSS 変数 `--choice-top` (既定 27%) と `--start-bottom` (既定 12%) で調整可。

## ② 価値・選好 (Stage 2) の課題仕様 (`?block=value`)

- **刺激**: 文字2択 (短語句)。上部中央に設問ステム (例「どちらが欲しいですか？」) を固定表示。reach-decision の操作は①と同一。
- **中核操作**: 価値差を3水準で段階化 — **明確** (価値差大→即断・高確信)・**中** (一長一短のトレードオフ)・**拮抗** (価値差最小→迷い)。拮抗は approach 型 (両方魅力) と avoidance 型 (両方イヤ「まだマシな方」) を含む。
- **4ドメイン混在** (消費財 / くじ / 食品 / 価値判断) で方略化を防止。左右CB (高価値側を左右均等)。
- **試行構成**: 24 項目 (価値差3 × ドメイン4 × 各2) を各1回 = **本番 24 試行** + 練習 (ゲート制)。左右CB は項目間で均等 (高価値側を12左12右、水準内4L/4R)。同一設問の2回提示はしない。くじは金額くじ (EV 記録) と賞品くじ (EV なし) の混合。
- **評定 (ON)**: 各試行の選択直後に 2 項目 × 5 段階 (自信 / 迷い。2026-07-15 に難しさを削除)。
- **正誤フィードバックなし** (主観選択のため)。試行メタに domain / 価値差水準 / conflict 型 / くじ EV 差を記録。設計正本は private リポ `research/sources/experiment-design.md §6`。

## ③ 道徳ジレンマ (Stage 2) の課題仕様 (`?block=moral`)

- **刺激**: 場面文ステム + 文字2択 (どうするかの行動選択)。reach-decision の操作は①②と同一。
- **試行構成**: 4類型 (sacrifice / honesty / loyalty / care) × 葛藤3水準 (明確 / 中 / 拮抗) × セル2項目 = **本番 24 試行** + 練習 (ゲート制)。
- 明確のみ規範整合 `betterSide` を定義 (中・拮抗は null)。左右CB。評定2項目 ON。読速ベースライン (短文3本) が開始前に付く。
- 設計正本は private リポ `research/sources/experiment-design.md §6-5`。

## ②③ 統合セッション (`?block=combo`) と ⑤ 注意チェック

- ②と③を1セッションで通す (第二パイロット以降の配布形態)。ブロック順は既定ランダム (被験者間CB、`?order=vm|mv` で固定可)。練習はセッション冒頭に統合 (本番ブロック順で各2問・1問目に評定チュートリアル)、事後アンケートは末尾で1回。
- **⑤ 注意チェック (既定ON、`?attn=0` で無効)**: 指示付き項目を②③に各2問埋め込み + 末尾に注意確認ミニブロック2問 (評定OFF)。完了画面でデブリーフィング (種明かし) を表示。
- データは `device.block="combo"`・`device.seq` にブロック順、各試行に `block` / `isCheck` タグ。解析側は per-trial `block` で value / moral を分離し `isCheck` 試行を主解析から除外する。

## クロスプラットフォーム実装上の注意

- iOS は静止中 `pointermove` を出さない / Android は出す → 生記録のまま保持し後処理で扱う
- 同一 `timeStamp` の重複イベントが発生しうる → `dt>0` ガード必須
- iOS は `timeStamp` 1ms 量子化、Android は小数
- 画面サイズ / DPR が機種で大きく異なる → surface 相対座標 + 毎試行 geometry 記録
- URL バー伸縮で viewport がずれる → 全画面 fixed + surface 相対で対応
- 画面端ドラッグが OS ジェスチャと衝突 → 選択肢を端から ~6% 内側にレイアウト + `touch-action: none`
- マルチタッチ二本目は無視、early release / 短すぎ試行は再呈示

## ローカル開発

リポ root の `serve.js` がリポ全体を配信するので、root からのパスでアクセス:

```sh
node ../serve.js   # http://127.0.0.1:8000/pilot-anchor/ で開く
```

HTTPS が必要なら GitHub Pages (公開済み) を使う。

## 技術

- 単一の静的 HTML ファイル + 静的サーバスクリプトのみ。ビルドステップなし、依存ライブラリなし。
- Pointer Events API ベース。
- データ保存: ブラウザ標準のダウンロード (Blob URL)。任意で `CONFIG.uploadUrl` に POST 先を設定可能。

## 由来

- 課題: 数値サイズ一致性 (Numeric-Size Congruity)。スマホ・タブレットでの reach-decision 版は Ouellette Zuk (2025) が確立。
- 修論研究の Stage 1 として作成。研究全体のドキュメント・解析計画・先行研究調査は別リポ (private) で管理。
- 取得系 (Pointer Events / `event.timeStamp` 生記録 / `getCoalescedEvents`) は同階層の [../sampling-rate-test/](../sampling-rate-test/) から流用 (60Hz floor の設計根拠もそこで確立)。
